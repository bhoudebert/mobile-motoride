# Shipping the app: Google Play and the App Store

How a release of MotoRide gets from `main` to riders' phones. It is written as a procedure to follow, with an honest
list of what the repository does **not** do yet (section 2): the app has been built and run as a development build on one
Android phone; the iOS app **compiles and packs in CI** (an unsigned IPA, ADR 0041) but **has never run on an iPhone, never been signed for release, never been submitted**. Read this with
[`EVOLVING.md`](EVOLVING.md) (how a change reaches `main`) and [`TESTING.md`](TESTING.md) (what must pass first).

Facts about the stores change; the ones that matter are dated and linked at the end. Check them again before each first
submission.

## 1. The path, in one picture

```
main (Conventional Commits) ── release-please PR ── merge ── tag vX.Y.Z + GitHub release
                                                                   │
                       npm run quality + npm run smoke:device (release build) must pass
                                                                   │
                    ┌──────────────────────────────────────────────┴────────────────────────┐
              Android build (AAB, signed)                                      iOS build (IPA, signed)
                    │                                                                       │
        Play Console: internal ▸ closed ▸ production                          TestFlight ▸ App Review ▸ release
```

## 2. What exists, and what is missing

| Exists                                                                                                                         | Missing before a first submission                                                        |
| ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Expo SDK 58 / React Native 0.88 project, application id `com.adequatefunction.motoride` for both stores                        | Store accounts (section 3) and a **privacy policy** page                                 |
| Release PRs and tags from release-please (`package.json` version); `app.config.ts` takes it from there                         | A privacy policy and the store declarations (section 3)                                  |
| `android/` generated by `expo prebuild` (ignored by git, ADR 0002)                                                             | Your **upload key** and its four GitHub secrets (section 5): until then no release build |
| A signing plugin and `npm run build:android`; a workflow that attaches the signed `.aab` and `.apk` to each release (ADR 0030) | iOS: `eas.json` and an Expo account, or a Mac                                            |
| Target API 36 (React Native 0.88's default)                                                                                    | iOS: built unsigned in CI, never run on an iPhone; background modes are set, untested    |
| Device smoke on a real Android phone                                                                                           | Store listing: description, screenshots, icon sizes, content rating                      |
| Foreground service for location on Android                                                                                     | Play's declaration of that service, with a video; the data-safety form                   |

Also: the app uses **free public services** (Nominatim, Valhalla, Overpass) whose usage policies are for light use, not for
an app with many riders. Before a public release, run your own (ROADMAP: "our own Valhalla and Overpass") or accept that the
app may be throttled; read each policy, and keep the `User-Agent` the app sends honest. The public Valhalla server (FOSSGIS) also asks the apps that
use it to send an identifying `X-Client-Id` (the app sends `motoride`) and to tell them through GitHub Discussions
(<https://github.com/valhalla/valhalla/discussions>, category of the demo server): **do that before the first public release.**

Decide these once, then the rest of this page is routine.

## 3. One-time setup

1. **Accounts.**
   - Google Play Console: one-time fee (US$25), identity verification. A _personal_ account created after 13 Nov 2023
     must run a **closed test with at least 12 testers opted in for 14 days** before Production can be requested; an
     organisation account does not (check the current rule, section 9).
   - Apple Developer Program: US$99 a year. Needed even for TestFlight.
2. **Identity.** The application id / bundle identifier `com.adequatefunction.motoride` cannot change after publication.
   Keep it, or change it **now** in `app.json` (`ios.bundleIdentifier`, `android.package`) and regenerate `android/`.
3. **Privacy policy** at a public URL; both stores require it. It must be truthful about what the app does:
   - the phone's position is used on the phone; it leaves the phone **only** when the rider turns on live sharing (to the
     rider's own server, **encrypted**, the server cannot read it);
   - to search a place, route to it or complete a GPX, the text searched or the route's coordinates go to **public**
     services (Nominatim `nominatim.openstreetmap.org`, Valhalla `valhalla1.openstreetmap.de`, Overpass
     `overpass-api.de` and `overpass.openstreetmap.fr`), and basemap tiles come from OpenFreeMap
     (`tiles.openfreemap.org`): they see those coordinates and the phone's IP address;
   - roadbooks and recorded rides stay on the phone; nothing is sent to the project.
4. **Legal review of the camera warnings** (ROADMAP, ADR 0021): in some countries (France) warning of the _position_ of a
   speed camera is forbidden; the app's policy is by country (exact, zones, off). Have this reviewed **before a public
   release**, and choose the countries you distribute to accordingly (Play and App Store both allow picking countries).
5. **Listing material**: name (MotoRide), short and long description, icon 512×512 (Play) and 1024×1024 (Apple), phone
   screenshots (the device smoke saves real ones in `.smoke/`), a feature graphic for Play (1024×500).

## 4. Versions

- The release-please PR bumps `package.json` and the changelog; merging it creates the tag. That is the **version**
  (`X.Y.Z`) users see.
- `app.config.ts` reads it from `package.json`, so the app, the `.aab` and the store show the tag's number. The Android
  `versionCode` (the ever-increasing number Play checks) is computed from it, `major × 1,000,000 + minor × 1,000 + patch`
  (`src/core/release.ts`): `1.0.0` is `1000000`, `1.2.3` is `1002003`. Nothing to maintain by hand, and a re-upload of the
  same version is refused by Play, as it should be.
- iOS needs its own build number (`CFBundleVersion`): `app.config.ts` gives it the same number as `versionCode`.

## 5. Build

### Android: GitHub builds and signs it

Every release PR you merge makes GitHub build the app and attach two files to the release (ADR 0030):

- `motoride-X.Y.Z.aab`, the **App Bundle** you upload to Google Play (Play does not take an APK);
- `motoride-X.Y.Z.apk`, the same app to install on a phone to try the release build (`adb install`, or open it from the
  phone's browser).

Both are signed with **your upload key**. Set it up once:

1. **Make the key on your own machine**, never in a chat or a repository, and keep the file and both passwords in your
   password manager (losing them means a support request to Google to reset the upload key):

   ```bash
   keytool -genkeypair -v -storetype PKCS12 -keystore motoride-upload.keystore \
     -alias motoride -keyalg RSA -keysize 2048 -validity 10000
   ```

2. **Give it to GitHub** (repository ▸ Settings ▸ Secrets and variables ▸ Actions, or with `gh secret set`):

   | Secret                      | Value                                                  |
   | --------------------------- | ------------------------------------------------------ |
   | `ANDROID_KEYSTORE_BASE64`   | `base64 -w0 motoride-upload.keystore`                  |
   | `ANDROID_KEYSTORE_PASSWORD` | the store password                                     |
   | `ANDROID_KEY_ALIAS`         | `motoride` (what you gave `-alias`)                    |
   | `ANDROID_KEY_PASSWORD`      | the key password (the same as the store's with PKCS12) |

3. **Try it** without making a release: Actions ▸ _Android release build_ ▸ _Run workflow_ on `main`. The files are in the
   run's artifacts for 30 days. Without the secrets the run says so and builds nothing; it never signs with the debug key.
4. In Play Console, enrol in **Play App Signing** at the first upload (section 7): Google keeps the key riders' phones
   check, and the key above is only the upload key.

To build on your own machine instead (in the Nix shell): put the same four values in `android/keystore.properties`
(`storeFile=`, `storePassword=`, `keyAlias=`, `keyPassword=`; `*.keystore` and the folder are ignored) or export
`MOTORIDE_KEYSTORE_FILE`, `MOTORIDE_KEYSTORE_PASSWORD`, `MOTORIDE_KEY_ALIAS`, `MOTORIDE_KEY_PASSWORD`, then
`npm run build:android`. The files are in `android/app/build/outputs/bundle/release/` and `.../apk/release/`.
`npm run build:android` regenerates `android/` (`expo prebuild --clean`), so run it only when you can afford to lose
hand edits there, and rebuild the development client after (`npm run android`) to go back to developing.

### iOS

Built on a GitHub macOS runner, not on this Linux machine and not with EAS: see section 8 (ADR 0042).

## 6. Before every release

1. `npm run quality` passes on `main`.
2. Install the **release** build (the release's `.apk`, or `npm run build:android`) on a real phone and run
   `npm run smoke:device` against it, then ride a short real route yourself, with sharing on and with the screen off.
   The smoke was written against the development build: if a check depends on the dev menu, fix the check, not the build.
3. The release PR is merged and its tag exists; the changelog is what you will paste into "What's new".
4. The privacy policy and the data-safety answers still match what this release does (a new network call changes them).

## 7. Android: Google Play

1. **Create the app** in Play Console (default language, free, app, not a game). Enrol in **Play App Signing**: Google
   keeps the key that signs what riders install; yours is only the _upload_ key.
2. **Fill the declarations** (Policy ▸ App content): privacy policy URL, ads (none), target audience (not for children),
   content rating questionnaire, and the **Data safety** form from section 3's list (location: collected only if sharing
   is on, sent to the rider's own server, encrypted in transit, optional).
3. **Foreground service**: the app runs location in a foreground service (`FOREGROUND_SERVICE_LOCATION`). Play asks you to
   declare it and to give a **short video** showing the feature (a ride with the notification) and what the user sees.
   Record it from a real ride.
4. **Tracks**, in order: _Internal testing_ (up to 100 testers, available in minutes, no review of the listing) ▸
   _Closed testing_ (needed for 14 days with 12 testers on a new personal account) ▸ _Production_. Upload the `.aab`
   with `eas submit --platform android` (needs a Play service-account key) or by hand in the console.
5. **Staged rollout** in Production (start at 10–20 %), watch Android vitals (crashes, ANRs), then widen.
6. The app must target API 36 or higher from 31 Aug 2026; React Native 0.88 already does.

## 8. iOS

### The signed build and TestFlight (ADR 0042)

`.github/workflows/ios.yml` (Actions ▸ iOS build ▸ Run workflow, and the Release workflow with each new tag) runs
`expo prebuild --platform ios`, archives and exports the app with Xcode on a GitHub macOS runner, signs it with your paid
account and uploads it to TestFlight. No Expo account, no EAS. macOS runner minutes are free on a public repository.

One-time setup:

1. **App Store Connect API key**: App Store Connect ▸ Users and Access ▸ Integrations ▸ App Store Connect API ▸ Team Keys ▸ +,
   role **Admin** (it must be allowed to create the distribution certificate). Download the `.p8` once; note the **Key ID** and
   the **Issuer ID** shown above the table.
2. **Team ID**: developer.apple.com ▸ Account ▸ Membership details.
3. **Four repository secrets** (Settings ▸ Secrets and variables ▸ Actions):

   | Secret          | Value                                               |
   | --------------- | --------------------------------------------------- |
   | `APPLE_TEAM_ID` | the 10-character Team ID                            |
   | `ASC_KEY_ID`    | the key's ID                                        |
   | `ASC_ISSUER_ID` | the issuer UUID                                     |
   | `ASC_KEY_P8`    | the whole content of the `.p8` file, with its lines |

4. Run the workflow by hand once. After 10 to 30 minutes of processing the build shows in App Store Connect ▸ TestFlight;
   add yourself as an internal tester (no review) and install from the TestFlight app.

Without the secrets the workflow still builds an **unsigned IPA** (ADR 0041) and attaches it to the release; sign it with
Sideloadly or AltStore (free Apple ID, 7 days). App Store Connect refuses a build number it has already received, so a
second run of the same version fails at the upload: bump the version, or untick "Upload the signed build to TestFlight".

Tried so far: the build compiles, MapLibre and every native module link, and the Info.plist carries the identifier, the
version, the build number (`CFBundleVersion`, the same number as Android's `versionCode`), the location strings and the
`audio`, `location` and `fetch` background modes. **Not tried: signing, the upload, or running it.** Expect a first round of
fixes on a phone.

### The App Store

Nothing past the build has been tried. Expect a first round of fixes, and treat the Android parity as unproven.

1. **The iOS settings are in `app.json`** (the `location` and `audio` background modes and the strings that say _why_).
   `ios.infoPlist.ITSAppUsesNonExemptEncryption` is `false`: the app only encrypts live-share positions (AES-256-GCM), a
   standard algorithm. Re-check that with the export-compliance questions in App Store Connect (France asks for a
   declaration of some encryption); change it if they say otherwise. The Android foreground service has no iOS equivalent: background
   updates come from the location background mode and the blue status-bar pill.
2. **Build and run**: the workflow above, then install from TestFlight on your iPhone to check that MapLibre and every native
   module run; fix what breaks.
3. **App Store Connect**: the app record exists with the bundle identifier; fill the **App Privacy** labels (same truth as
   section 3), the age rating and the EU **trader status**.
4. **TestFlight**: testers install from TestFlight (internal testers need no review; external ones need a short Beta App
   Review).
5. **App Review**: submit for review with **review notes**: what the app does, why it uses location in the background
   (turn-by-turn corner warnings while the screen is off), a demo roadbook to open, and, for live sharing, a server and an
   **invitation or token that works** for the reviewer (or say sharing is optional and off by default). An app that cannot
   be exercised without a private server is a common reason for rejection.
6. Builds must come from the iOS 26 SDK / Xcode 26 since 28 Apr 2026; check that `macos-latest` has Xcode 26 (the workflow prints the version).
7. Release manually or automatically once approved; use phased release.

## 10. What to automate later

Android is built on every release; **uploading** to Play is still by hand (the first upload must be, and Play needs a
service-account key to do it from a workflow). iOS already goes to TestFlight from the release (section 8). Not before one release has gone through by hand: the first one shows what the stores ask.
